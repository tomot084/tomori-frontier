# ステージとコンテンツの追加方法

Tomoriは灯芽の群島と霜灯群島の2ステージを持つ。各ステージは3エリア、橋・門・灯台、拠点、資源、生産ライン、設備、宝箱、敵の群れで構成する。既存の設備を別のステージに配置する際、描画や仕事のAIをコピーしない。

## 配置データと共通の実装

| ファイル | 役割 |
| --- | --- |
| `src/stages.ts` | ステージID・名称・接続先、3エリアの色・敵構成、建築目標・費用、拠点、設備位置、解放順、宝箱、資源の種 |
| `src/content.ts` | 再利用するコンテンツのID・名前・価格・説明・投資カテゴリ、保存する在庫キー |
| `src/settlements.ts` | 果樹園、採集班、窯、運搬・分岐、減速、守護獣、宝箱の仕事と判定 |
| `src/settlement-view.ts` | 予定地・完成設備・作業員・在庫・可動部・攻撃予兆の3D表現 |
| `src/world-machines.ts`, `src/machine-view.ts` | コンテキストに沿った砲台・採掘機・回収塔の仕事と表現 |
| `src/investments.ts`, `src/ui.ts` | 共通の購入・価格・前提条件・近接操作。新しい巨大メニューは作らない |
| `src/data.ts` | 既存version 1の検証と任意のステージ・在庫・探索記録の読み込み |

実行中のGameModelは自分の`stage`を持つ。地形・建築・カメラ・NPC・投資・生産ラインは同じ定義を参照する。グローバルな座標配列を書き換えないため、異なるステージのGameModelを同時に作っても配置が混ざらない。

## 同じ形式の別ステージを追加

1. `frostStage`を参考に、新しい`StageDefinition`を定義する。IDは公開後も固定する。
2. 3つの`areas`へID・名前・地面色・崖色・敵タイプを指定する。現在の三島テンプレートの地面範囲と中央の接続を使う。
3. `buildings`へ橋・門・灯台の名前と必要素材を指定する。進行はこの費用を使って判定される。
4. `layout`へINPUT・鋸・OUTPUT・市場・客・金庫・砲台・採掘機・回収塔の位置、`camps`へ回復拠点を指定する。製材ラインは右から左へ流す配置を使う。
5. `contents`に必要な設備を配置する。`unlock`は0が最初の島、1が橋の先、2が門の先。設備は一部だけ選んでも動く。必要なら各配置の`price`で共通価格を上書きする。
6. `machineRules`で砲台・採掘機・回収塔などの価格や解放条件を変えられる。採掘場所の資源IDを変更する場合は`drillNodeId`を指定する。砲台は現在開放済みのエリアの敵を探す。
7. `treasures`へ一度だけ開く宝箱、`resourceSeed`へ資源の配置の違いを指定する。
8. `stages`へIDで登録し、`destination`と航路の配置をつなぐ。必ず帰れる接続先も用意する。

```ts
const stage: StageDefinition = {
  ...frostStage,
  id: "new-region", name: "新しい群島", destination: "frontier",
  contents: [
    { id: "orchard", x: 740, y: 580, unlock: 0 },
    { id: "lumberCamp", x: 170, y: 900, unlock: 1 },
    { id: "kiln", x: 180, y: 1600, unlock: 2 },
    { id: "portal", x: 740, y: 230, unlock: 0 },
  ],
};
stages[stage.id] = stage;
```

数値だけでなく、色・地形・樹木・敵の役割、働く設備の順番や位置を変える。霜灯群島は実際の再利用例で、雪色の霜根の森、青い晶石渓谷、暖色の熔灯高原、別配置の設備と敵を持つ。

## コンテンツを増やす

同じ仕事を別のステージへ置く場合は`contents`の行を追加する。同一のContentIdは各群島で1基。新しい仕事そのものを追加する場合は、安定したContentIdと共通カタログ、シミュレーションの仕事、3D表現を1回追加する。購入・解放・保存・全体一覧はそのIDを使う。

既存の仕事は`harvest`・`orchard`・`courier`・窯の加工・減速・守護獣の判定に分かれている。新しい仕事で保存する在庫は`workshopKeys`へ追加する。最大量と、受け取り・加工・出荷のどの瞬間に在庫を移すかを明確にする。

描画は未購入の予定地を小さな1メッシュにまとめる。完成モデルと作業員は必要になった時にだけ生成し、550以内だけ表示する。在庫は最大24個のthin instance、搬送物は資源ごと最大24個の再利用プール。NPCや設備の影対象は増やさない。

## 保存と資源の約束

資源・灯貨・装備・累計撃破は主人公に付いて移動する。建築進行・設備・市場・製材・在庫・開封した宝箱・守護獣の討伐は群島ごとに保存する。現在のステージは従来のSaveのトップレベルを使い、離れているステージは`worlds[id]`へ保存する。旧セーブに`stage`がなければ灯芽の群島としてそのまま続ける。

運搬物は保存済み在庫の予約として扱う。持っている見た目を作った瞬間に在庫から消さず、実際に到着・出荷した時に消費する。再読み込みすると作業は再開するが、予約していた素材は失われない。加工も完了時に原料を消費する。

分岐の運搬係と従来の運搬係・主人公は共通のOUTPUT予約数を参照する。取り合いや二重出荷を避けるため、新しい運搬者もこの予約に参加させる。

新しい採集班を追加しても、未購入の製材所を離れた場所から勝手に動かさない。製材を自動化するのは購入済みのコンベアか製材担当。

## 追加時の検証

- IDと在庫の保存復元、移動中・加工中の数量保全、前提条件、所持上限。
- 別のGameModelの座標や進行を変えないこと。
- ステージを往復して、建築・設備・宝箱・討伐状態が復元されること。
- 390×844で予定地→購入→実物→作業を確認し、前後の画像を比較すること。
- 描画距離・ドロップ128個・敵96体・演出48個・搬送各24個の上限。新しいエリアは同時に描画せず、現在の群島だけ動かす。
